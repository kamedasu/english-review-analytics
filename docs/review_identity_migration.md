# レビュー識別とPhase 2移行手順

## 記録方法は変更しない

ChatGPTのレビューMarkdownをNotion月ページへ貼り付ける現在の運用を継続する。テンプレート変更、ID入力、Notionプロパティ追加、Notion DB化は不要。アプリは既存のブロック取得レスポンスから見出しIDを取り出すため、レビューごとの追加APIリクエストも不要。

## 識別方式

- 新規の内部固定ID: `notion:<source_block_id>`。
- 既存review_id: そのまま固定IDとして維持。現在のIDに日付やハッシュが含まれていても、編集時に作り直さない。
- `source_block_id`: 実際のNotion heading_1ブロックのID。日付・種別・出現順で置換しない。
- `content_hash`: 現在の本文SHA-256。現在のprocessedとの一致でスキップする。旧stateの過去ハッシュでスキップしないため、A→B→Aも更新できる。
- 同じブロックの内容・日付・種別の編集は、同じreview_idの更新になる。
- ページやブロックが消えても保存済みレビューを自動削除しない。ページ間移動、見出し再作成、競合は保留する。

## Markdownとブロックの対応

`NotionPage.review_blocks`が、Markdownの各レビューと出典ブロックを保持する。リスト子ブロックのインデントを維持し、コンテナ内の子ブロックも変換する。通常のraw Markdown形式は維持し、`raw/<title>_<page_id>.identity.json`にページハッシュ、各レビューのブロックID・本文ハッシュ、保留理由を保存する。

本文・コード内に見出しに見えるテキストがあり、解析境界を信頼できない場合はページ全体のレビューを保留する。ブロックIDとMarkdownの対応不一致、重複ブロックIDは保存前に同期を中断する。

## stateと既存データ

`FetchState`に以下を追加する。

- `identity_version: 2`
- `source_bindings`: ブロックID → 固定review_id
- `current_reviews`: 固定review_id → 現在版の状態
- `pending_sources`: 確認待ちのブロックID → 保留理由。過去raw候補は本文を編集しても確認なしに新規登録されない。

旧`reviews`辞書は履歴として保持し、新しいスキップ判定には使わない。processedが欠けていても、確定済みbindingがあれば元の固定IDで再保存できる。bindingもない過去rawの候補は復元せず保留する。

processedには任意の`source_block_id`を追加する。未移行・対象外レビューには空フィールドを追加しない。対象外ページのraw・既存stateレコード・processedの行は保持する。集約JSONファイル自体は従来どおり全レビューを含めて保存する。

旧形式レビューへの自動対応付けは、同じページ内で本文ハッシュ全文が取得側・保存側とも一対一に一致し、他のブロックに既に割り当てられていない場合だけ行う。この場合は解析済みフィールドや内部参照を書き直さず、出典IDを補う。

初回対応付け前に編集されたレビュー、新旧見出しの対応が不明なレビュー、完全コピー、過去rawにだけ存在する候補は保留する。既存の見出しが消えているページでは、新規ブロックの自動追加も保守的に保留する。対応が確定した既存見出しが残っていれば、同日の別見出しを新規登録できる。

保留数を同期結果に表示し、補助JSONに理由を記録する。Notion側の追加操作は不要。保留解除は、アプリ側の移行計画・レビュー確認で扱う。

## 空レビュー

見出し、日付、Topicだけでは有効レビューにしない。構造化された学習内容、または正の学習時間とTopicの両方が必要。空見出し・解析失敗は既存レビューを置き換えず、保留する。過去に保存された空項目も、このコードを起動しただけでは削除しない。

## 保存とRAG

通常表示・同期対象未指定時はNotion APIを呼ばない。同期は`NOTION_PAGE_IDS`にあるページだけ。全ページ取得・タイトル検証後に保存する。

Localは一時ファイルからの`os.replace`で各ファイルを更新する。Local/S3とも、raw・補助JSON・processedを書き、stateを最後に保存する。保存失敗時は変更したファイルを復元する。複数ファイルの更新は単一トランザクションではない。強制終了、継続的ストレージ障害、同じ保存先への同時同期には完全な原子性はない。同時同期や新旧コードの混在を避ける。

RAG文書IDの`review_id:文書種別:項目番号`とメタデータ形式は維持する。既存IDへの出典追加だけではEmbeddingや全面再構築は不要。内容変更・確認済み復元分のみ増分更新する。保留があっても保存に成功した有効レビューはRAG更新の対象となり、保留した本文そのものは追加されない。RAG更新失敗は従来どおり画面で別途報告する。

## 移行ツール（既定は読み取り専用）

```sh
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -B scripts/migrate_review_identity.py
```

実際の`DATA_ROOT_DIR`のraw・processed・stateを読み、候補の日時・本文ハッシュ・保存件数をJSONで標準出力する。APIアクセス、保存、RAG生成は行わない。別のローカルスナップショットには`--data-root /path/to/snapshot`を指定する。S3本番のデータ移行CLIはこのPhaseでは提供しない。共有の同期・計画・対応付け処理と保存復元はモックS3でも検証する。

対応付けの適用は、ブロックIDを含む補助JSONが得られ、計画をレビューした後だけ行う。確認ファイルの形式:

```json
{
  "expected_sha256": {
    "processed/reviews.json": "<確認したファイルのSHA-256>",
    "state/state.json": "<確認したファイルのSHA-256>"
  },
  "bindings": [
    {"review_id": "<既存の固定ID>", "source_block_id": "<確認済み見出しID>"}
  ]
}
```

`--bindings /path/to/reviewed.json`のみなら検証・試算だけ。`--apply`を明示した場合のみ、検証済みの既存レビューへの対応付けを保存する。適用時も、raw・RAG・Notionには書き込まない。入力ハッシュ不一致、ID競合、非一対一、空レビュー、rawとの不一致は拒否する。候補54件の追加、既存レビューの削除、見出し再作成への再割当はこの適用機能に含めず、別途確認済みの復元手順として扱う。

## Phase 2の順序（今回未実施）

1. アプリの同期・RAG更新を停止し、最新のバックアップを検証する。
2. 54候補の独立性と、10月25日の空項目の扱いを確認する。件数・学習時間・RAG増分の予定を作る。
3. 許可されたNotion読取で見出しIDを取得し、まず別の作業用スナップショットで対応表を作る。現在の保存rawだけからブロックIDを推測しない。
4. 確実な既存レビューだけ対応付ける。確認ファイルを試算し、曖昧なものは保留する。
5. 確認済み候補のみを復元する別の適用計画をレビューする。旧stateを削除しての一括再同期は禁止。
6. processed・state・内部参照・対象外月の不変性を確認し、RAGを増分更新する。
7. 同じ入力を繰り返し、重複登録や不要なEmbeddingがないことを確認する。

## バックアップと復元

Phase 1バックアップ: `data_backup_20261103_154147/`。コピー元はプロジェクトの`data/`。raw、processed、state、Chroma SQLite・ベクトルファイルを含む18ファイル、31,073,583バイト。`backup_manifest.json`に元ファイルのサイズとSHA-256を記録した。manifest自身は18ファイルの集計外。コピー前後の元データ・コピー先の全ハッシュが一致し、コピー先SQLiteのquick_checkはokだった。調査時、対象ファイルを開いているプロセスはlsofで検出されなかった。

復元前にアプリ・同期・RAG更新を停止する。manifestの全ファイルを再検証し、現在のデータも別バックアップに保持する。既存ディレクトリへの上書きマージは行わず、空の復元先へraw・processed・state・chromaをまとめて戻す。たとえば既定パスの場合の手順は次のとおり（今回実行しない）。

```sh
# アプリ等を停止し、バックアップのハッシュを確認してから実行する
mv data data_backup_before_restore_YYYYMMDD_HHMMSS
mkdir data
cp -a data_backup_20261103_154147/raw data/
cp -a data_backup_20261103_154147/processed data/
cp -a data_backup_20261103_154147/state data/
cp -a data_backup_20261103_154147/chroma data/
```

復元後もハッシュを照合してから起動する。コードを旧版に戻す場合も、旧版が新しい出典情報を捨てないよう、対応するデータ一式と合わせて戻す。バックアップと移行確認JSONには学習記録が含まれるためGit管理しない。`data_backup_*/`は`.gitignore`で除外済み。
